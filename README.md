# PUF-Based UAV Swarm Authentication

A four-phase authentication protocol for drone swarms, rooted in a hardware
fingerprint (a Physical Unclonable Function) rather than in a stored key, with a
full OMNeT++ 6.3 implementation and evaluation.

The specification and write-up are in
[`revised_theory/paper.tex`](revised_theory/paper.tex); the implementation is under
[`src/`](src/); results land in [`simulations/results/`](simulations/results/).

## 1. How to run it

### Prerequisites

| Requirement | Version used | Notes |
|---|---|---|
| OMNeT++ | 6.3.0 | expected at `~/omnetpp-6.3.0` |
| C++ compiler | clang or g++, C++17 | OMNeT++ supplies clang |
| OpenSSL **development headers** | 3.5.5 | `libssl-dev`; supplies SHA3, HMAC, HKDF, ChaCha20-Poly1305, X25519 |
| Python | 3.8+ | analysis scripts use **only the standard library** — no virtualenv needed |
| GNU make, bash | any recent | |

Nothing else. No libsodium, no `libcorrect`, no Python packages. SPONGENT-160 and
Ascon-128a are in the source tree, so there is nothing to fetch.

Check OpenSSL is present with headers:

```bash
ls /usr/include/openssl/evp.h && openssl version
```

### Set up the environment (every new terminal)

OMNeT++'s `setenv` activates its own bundled Python virtualenv, which can shadow the
system Python. The analysis scripts need no virtualenv, so this sequence is enough:

```bash
cd ~/UAV-OMNET++
source ~/omnetpp-6.3.0/setenv > /dev/null
export PATH="$HOME/omnetpp-6.3.0/bin:$PATH"

which opp_makemake     # -> ~/omnetpp-6.3.0/bin/opp_makemake
```

### Build

```bash
scripts/build_omnet_project.sh
```

Produces `src/uavauthsim`. **Always use this script, never bare `make`.** The
`Makefile` is generated by `opp_makemake` with a fixed object list and is
git-ignored, so a newly added source file is only picked up when the script re-runs.
Extra compiler flags belong in `src/makefrag`, which survives regeneration.

```bash
BUILD_MODE=debug scripts/build_omnet_project.sh    # debug build
```

### Run the tests (fast gate, about two minutes)

```bash
bash tests/run_tests.sh              # all nine suites
bash tests/run_tests.sh bch          # one suite, by name substring
```

Expected tail:

```
=== 9 passed, 0 failed ===
```

These binaries do not link the simulation kernel, so they build and run in seconds.
Each test declares its own dependencies in a `// DEPS: <paths under src/>` comment,
so adding a test needs no edit to the runner.

### Run the simulation

One configuration, one repetition:

```bash
cd simulations
../src/uavauthsim -u Cmdenv -n ../src:../simulations -f omnetpp.ini -c StadiumSHA3 -r 0
```

The full campaign, with export and analysis:

```bash
python3 scripts/run_experiments.py --skip-build --runs 10 \
        --configs StadiumSHA3 StadiumSPONGENT Baseline5UAV Swarm20 ArbiterPuf HighNoise
python3 scripts/analyze_results.py
```

Useful flags: `--clean` archives previous results into
`simulations/results/archive/<timestamp>/` instead of deleting them; `--runs N`
limits repetitions; omit `--skip-build` to rebuild first.

## 2. The protocol explained

### The problem, and the idea

Drones in a swarm must verify who they are talking to before accepting commands or
relaying data. The usual answer is to store a secret key on each drone — but a drone
can be captured, and a stored key can be read out of captured hardware.

A **Physical Unclonable Function (PUF)** avoids storing anything. Microscopic,
uncontrollable variations in how a chip is manufactured make each chip respond
slightly differently to the same electrical stimulus. Give the chip a *challenge*
`C` and it returns a *response* `R = PUF(C)` that no other chip reproduces and that
nobody — including the manufacturer — can predict. The secret is the silicon itself:
capture the drone and there is no key to extract.

One complication: the response comes back slightly different each time (temperature,
supply voltage, ageing), so it cannot be used directly as a key.

### Notation

| Symbol | Meaning |
|---|---|
| `UAV_i`, `GS` | drone *i*; ground station |
| `PUF_i(C)` | drone *i*'s response to challenge `C` |
| `mk_i` | drone *i*'s master key — **never stored** |
| `P_i` | public helper data (safe to publish) |
| `mk_GS` | ground-station master key, never leaves the GS |
| `Cred_ij` | credential for the pair *(i,j)* only |
| `SK_i`, `SK_ij` | session keys |
| `TID_i` | rotating temporary identity |
| `N_x`, `T_x` | 128-bit nonce; timestamp |
| `g^a`, `g^ab` | ephemeral public share; shared Diffie–Hellman secret |
| `MAC_K`, `KDF`, `AE` | keyed authenticator; key derivation; authenticated encryption |
| `‖`, `⊕` | concatenation; bitwise XOR |

### Turning a noisy fingerprint into a stable key

A **fuzzy extractor** solves the noise problem with two operations.

**Enrollment** takes a reading `R`, picks a random codeword `c` from an
error-correcting code, and publishes the difference:

```
s  = R ⊕ c
mk = KDF( Ext_seed(R) )
P  = (s, seed)          <- public
```

**Reproduction** takes a fresh, slightly different reading `R'` plus the public `s`:

```
w = R' ⊕ s = c ⊕ e      <- a slightly corrupted codeword
  --decode-->  c
R = s ⊕ c               <- the original reading, exactly
mk = KDF( Ext_seed(R) ) <- the same key as at enrollment
```

Because `R'` differs from `R` in only a few bits, `w` is a codeword with a few
errors; the code cleans it up and the identical key comes back.

We use **BCH(255, 131, 18)**: 255-bit blocks, correcting up to *t* = 18 flipped
bits. There is a subtlety that drives the whole design. The published `s` leaks up
to `n − k = 124` bits about `R`, so each block only *nets*

```
ρ·n − (n − k)     bits of secrecy      (ρ = min-entropy rate of the PUF)
```

With `L` blocks the requirement is

```
L · ( ρ·n − (n−k) )  ≥  ℓ + 2·log2(1/ε)
```

With ρ = 0.95, key length ℓ = 256 and ε = 2⁻⁶⁴, each block contributes 118.25 bits,
so **L = 4** gives 473 ≥ 384. This is *enforced in code* — the extractor refuses to
start if the budget is not met. It also explains why blocks are 255 bits rather than
128: a 128-bit block would leak 124 of its own 128 bits and contribute almost
nothing.

### Phase 1 — Enrollment (once, in a trusted facility)

```
GS reads the PUF:      R  <- PUF_i(C_i)
Run the extractor:     (P_i, mk_i) <- FE.Gen(R)

GS stores:     < TID_i, C_i, P_i, mk_i >   in protected memory
Drone stores:  < TID_i, C_i, P_i >         all public
```

**The drone keeps no secret.** Identity, challenge and helper data are public by
design. The master key exists only for the microseconds it is in use.

### Phase 2 — Drone ↔ ground station (4 messages)

The drone first regenerates its own key, locally:

```
mk_i        <- FE.Rep( PUF_i(C_i), P_i )
K_auth^i    =  KDF( mk_i ; "p2-auth" )
```

```
M1  UAV -> GS   < TID_i, N1, T1, g^a, σ1 >
                σ1 = MAC_{K_auth^i}( "M1" ‖ TID_i ‖ N1 ‖ T1 ‖ g^a )

M2  GS  -> UAV  < N2, T2, g^b, σ2 >
                σ2 = MAC_{K_auth^i}( "M2" ‖ TID_i ‖ N1 ‖ N2 ‖ T2 ‖ g^a ‖ g^b )

M3  UAV -> GS   < σ3 >
                σ3 = MAC_{K_auth^i}( "M3" ‖ transcript )

M4  GS  -> UAV  < AE.Enc_{SK_i}( {Cred_ij}, TID_i^new ) >
```

Both sides then derive the same session key from the transcript:

```
SK_i = KDF( mk_i ‖ g^ab ‖ transcript ; "p2-sess" )
```

Three things make this work where a naive challenge–response would not:

- **Every authenticator is keyed.** σ1, σ2, σ3 are MACs under a key derived from the
  PUF, so only the genuine drone (via its silicon) or the genuine GS (via its
  database) can produce them. A plain hash over values that are visible on the wire
  would prove nothing, since anyone could recompute it.
- **The drone checks σ2 before doing anything else.** A fake ground station gets *no
  reply at all*. This matters because a drone that answered arbitrary challenges
  would be an interrogation oracle: collect enough challenge–response pairs and you
  can machine-learn a software clone of the PUF.
- **The raw response never leaves the drone.** `FE.Rep` runs on-device; only MACs
  over public values are transmitted. There is nothing on the wire to harvest.

### Phase 3 — Drone ↔ drone (3 messages, no ground station)

Each *pair* gets its own credential, derived by the GS and delivered encrypted
inside M4:

```
Cred_ij = KDF( mk_GS ; "pair-cred" ‖ min(i,j) ‖ max(i,j) )
K_auth^ij = KDF( Cred_ij ; "peer-auth" )
```

```
P1  UAV_i -> UAV_j   < n_i, T, g^a', τ1 >
                     τ1 = MAC_{K_auth^ij}( "P1" ‖ i ‖ j ‖ n_i ‖ T ‖ g^a' )

P2  UAV_j -> UAV_i   < n_j, g^b', τ2 >
                     τ2 = MAC_{K_auth^ij}( "P2" ‖ i ‖ j ‖ n_i ‖ n_j ‖ g^a' ‖ g^b' )

P3  UAV_i -> UAV_j   < τ3 >
                     τ3 = MAC_{K_auth^ij}( "P3" ‖ transcript )

SK_ij = KDF( Cred_ij ‖ g^a'b' ‖ transcript ; "peer-sess" )
```

**Why per-pair credentials matter.** With one swarm-wide secret, capturing *any*
drone compromises *every* link. Here, capturing drone *k* exposes only the *N−1*
credentials involving *k* — measured at 3 of 6 pairs in a four-drone test.

Each message carries a distinct type tag (`"P1"`, `"P2"`, `"P3"`) plus a nonce and
timestamp, so a token from one step cannot be replayed as another (a reflection
attack).

### Phase 4 — Session keys and forward secrecy

Both session keys have the same shape:

```
SK = KDF( k_lt ‖ g^xy ‖ transcript ; label )
       ^^^^
       mk_i  (Phase 2)  or  Cred_ij  (Phase 3)
```

The ephemeral scalars are **erased** after use, and the exchange is **mandatory** —
there is no code path that skips it. So even if the long-term key is later
compromised, past sessions stay secret: recovering `g^xy` from the recorded `g^x`,
`g^y` is the Diffie–Hellman problem.

### Security properties, and what they rest on

| Property | Mechanism |
|---|---|
| Mutual authentication | keyed MACs in both directions under a PUF-derived key |
| No interrogation oracle | verify-before-respond; response never transmitted |
| Replay resistance | nonce cache + timestamp window + per-message type tags |
| Peer authentication | per-pair credential delivered under authenticated encryption |
| Capture resistance | no stored secret; damage bounded to *N−1* links |
| Forward secrecy | mandatory ephemeral exchange, scalars erased |

## 3. How it is implemented

### Layout

```
src/
  core/       Bytes.{h,cc}          byte/bit utilities, constant-time compare
              Encoding.{h,cc}       the canonical message encoder
  crypto/     CryptoSuite.h         abstract interface both profiles implement
              Sha3Suite.{h,cc}      SHA3 / HMAC / HKDF / ChaCha20-Poly1305
              SpongentSuite.{h,cc}  SPONGENT / keyed sponge / Ascon
              spongent/Spongent160  the sponge permutation
              ascon/Ascon128a       the AEAD
              X25519.{h,cc}         key exchange, with scalar erasure
              Drbg.{h,cc}           deterministic random generator
              OsslCommon.{h,cc}     fetch-once OpenSSL handle cache
              PrimitiveCounters     per-primitive cost measurement
  puf/        PufModel.h            interface + sub-challenge derivation
              IdealPrfPuf           idealised model (keyed PRF)
              ArbiterPuf            128-stage additive-delay model
              XorArbiterPuf         XOR of k chains
              MinEntropy            NIST SP 800-90B estimators
  fe/         BchCodec.{h,cc}       BCH(255,131,18)
              FuzzyExtractor        Gen/Rep, three profiles, budget check
  protocol/   Wire.{h,cc}           message types, field tags, TLV message
              Protocol.{h,cc}       all four phases, both sides
  nodes/      UavNode, GroundStationNode, WirelessMedium, AttackerNode
tests/        9 suites + committed reference test vectors
scripts/      build, run, export, analyse
simulations/  network, scenarios, results
```

### Key implementation decisions

**One encoder serving three jobs.** Every message is serialised by a single function
whose output is simultaneously the bytes on the wire, the input to the MAC, and the
byte count used for transmission delay. Each field is `tag ‖ length ‖ value` with
tags in ascending order, which makes the encoding *injective* (no two field sets
share a byte string) and *canonical* (one encoding per field set). Because there is
one encoder, those three uses cannot drift apart — and length prefixes mean
`"AB"+"C"` can never be confused with `"A"+"BC"`. Reading an absent field raises an
error instead of silently returning empty bytes.

**Two interchangeable crypto profiles** behind one interface, chosen by a parameter:

| | `sha3` (software) | `spongent` (constrained hardware) |
|---|---|---|
| Hash | SHA3-256 → 160 bits | SPONGENT-160/160/16 |
| MAC | HMAC-SHA3-256 | prefix keyed sponge |
| Key derivation | HKDF | one-pass sponge |
| Encryption | ChaCha20-Poly1305 | Ascon-128a |
| Key exchange | X25519 | X25519 |
| Hash/MAC level | 128-bit | **80-bit** (capacity 160) |
| Source | OpenSSL 3.5 | in-tree |

*Why the sponge profile does not use HMAC*: HMAC requires the key to fit inside the
hash's block, and SPONGENT-160's rate is **2 bytes** — smaller than any useful key,
so the construction is undefined there. The standard prefix keyed-sponge
construction (as in KMAC) is used instead; a sponge with non-zero capacity is not
length-extendable, so HMAC's nesting is unnecessary anyway. The resulting 80-bit
level is stated openly rather than implied to be 128.

**Domain separation everywhere.** Distinct leading bytes separate the hash, MAC and
KDF modes, and every derived key carries a unique label (`p2-auth`, `p2-sess`,
`pair-cred`, `peer-auth`, `peer-sess`, `tid-rotate`), so a key made for one purpose
can never be mistaken for another.

**Reproducible randomness.** All nonces, ephemeral scalars, seeds and challenges
come from a deterministic generator seeded from the simulator's RNG, not from the
library's entropy source. Ephemeral X25519 keys are loaded from those bytes rather
than generated internally. A whole run, including every ephemeral key, is therefore
reproducible from its configured seed.

**The BCH generator is checked, not assumed.** It is built as the product of the
minimal polynomials of α¹…α²ᵗ over the *complete* conjugate closure, which for
*t* = 18 contains 124 roots. The code asserts at construction that `deg g = 124` and
that all coefficients are binary — a non-binary coefficient would mean the closure
is incomplete. Getting the parity length wrong (for instance taking it as
`m·t = 144`) would give `k = 111 < 128` and silently leave part of every response
unprotected, so it is verified rather than trusted.

**Everything fails closed.** If the fuzzy extractor cannot decode a block it returns
*no key* — never a partial or uncorrected one. Authenticated-decryption failure
aborts the handshake and clears the output. A degenerate Diffie–Hellman point is
rejected rather than yielding a zero key. Suite selection throws on an unknown name
rather than silently defaulting, which would mislabel every result in a run.

**Realistic PUF noise.** Noise is added to the internal *timing difference*, not by
flipping output bits:

```
Δ' = Σ_i w_i·φ_i + N(0, σ)        r = 1 if Δ' > 0 else 0
```

Bits whose race is nearly tied flip far more often than the rest, as real silicon
behaves. The measured spread of per-bit flip rates is about **98×** that of a uniform
flip model. A calibration routine converts a target bit-error rate into σ.

**Protocol logic is transport-free.** The Phase 1–4 classes take bytes in and bytes
out with no reference to the simulation kernel, so the whole exchange is driven over
an in-memory transport in `tests/test_protocol_offline.cc`. Protocol correctness is
therefore established before any network code is involved.

**One transmission path.** A single `WirelessMedium` module owns the delay model
(propagation from node coordinates + serialisation + processing + jitter, each
reported separately), so there is exactly one definition of what a hop costs. It is
also the interception point for the adversary; with no attacker present it forwards
immediately, so attack and baseline runs stay comparable.

### Verification

Nine test suites, about 432,000 assertions. Everything is checked against published
reference values where they exist:

| Component | Checked against |
|---|---|
| SHA3-256, HMAC-SHA3 | NIST FIPS 202 / CAVP |
| HKDF | RFC 5869 A.1–A.3 |
| ChaCha20-Poly1305 | RFC 8439 §2.8.2 |
| X25519 | RFC 7748 §6.1, plus low-order-point rejection |
| **Ascon-128a** | **all 1,089 official LWC test vectors** |
| SPONGENT-160 | byte-exact against the designers' reference implementation |
| BCH(255,131,18) | `deg g = 124`; `g(x)` divides `x²⁵⁵+1`; **18,000 trials**, weights 1–18, all recovered exactly |
| Four-phase protocol | key agreement on both sides; every single-bit flip rejected |

On honesty: **no official test-vector file exists for SPONGENT**, so the code says
exactly that. `Spongent160::verificationStatus()` and `asconVerificationStatus()`
return strings recording what was and was not verified, and a test fails if the
caveat is removed. Neither in-tree primitive has had side-channel analysis; that is
stated too.

### How the statistics are computed

**The unit of replication is the run, not the CSV row.** Rows within one run share a
random stream and a scheduling epoch, so they are correlated. Intervals are computed
in two stages: a mean per run, then a *t*-interval across run means with *R−1*
degrees of freedom. Pooling all rows instead would inflate the degrees of freedom
from 9 to 99 and shrink every interval by roughly √10.
`scripts/stats_util.py` refuses to form an interval from fewer than three runs.

Success rates additionally carry a **Wilson** interval, and where no failure is
observed the **rule-of-three** bound is reported: 100 successes out of 100 means
"failure probability at most about 3 %", not "perfectly reliable".

| Noise | `bch255-131-18` | `bch255-91-25` | `rep3-bch255-131-18` |
|---|---|---|---|
| 1 % | 0.000 | 0.000 | 0.000 |
| 3 % | 0.033 | 0.000 | 0.000 |

**20 of 21 points fall inside the 95 % interval of the binomial prediction.** That

returned its input unchanged would produce a curve independent of the code
parameters.

### Attack outcomes

| Attack | Configuration | Attempts | Succeeded | Expected |
|---|---|---|---|---|
| GS impersonation | full protocol | 8 | **0** | fail ✓ |
| Message replay | full protocol | 1 | **0** | fail ✓ |
| Credential sniffing | full protocol | 10 | **0** | fail ✓ |
| GS impersonation | *ablation: no verify-before-respond* | 8 | **1** | succeed ✓ |

The last row is a deliberate **ablation**: one mechanism is disabled and the *same*
attacker code is run. It succeeds there and fails against the full protocol, which
is what makes the zeros meaningful — otherwise "all attacks failed" would be equally
consistent with a broken adversary.

| Scheme | Operation | Median |
|---|---|---|
| RSA-2048 | verify | 32.0 µs |
| RSA-2048 | sign | 1048.6 µs |
| ECDSA P-256 | sign / verify | 43.6 / 109.0 µs |
| ECDH P-256 | derive | 91.0 µs |
| X25519 | keygen / derive | 65.6 / 125.7 µs |

### Three findings worth reading carefully

**Reliability has a real limit.** At 5 % noise, 21 of 100 drones cannot regenerate
their key and never even start authenticating. This is why two success rates are
recorded — among drones that *tried*, and among *all* drones. Only the second reveals
those 21 failures; the first would report 100 %.

**The "lightweight" profile is not faster in software.** Its MAC costs 225 µs against
2.14 µs, roughly 100× more — yet end-to-end handshake latency differs by 0.4 %
(1.5085 vs 1.5030 ms), because the shared work dominates (key exchange ≈ 96 µs, PUF
and extractor ≈ 1.4 ms). SPONGENT's advantage is **chip area**, not software speed.

**Performance is comparable to elliptic-curve schemes, not dramatically better.**
Each handshake does about 190 µs of public-key work against 91–155 µs for
ECDH/ECDSA — the direct cost of making forward secrecy mandatory. The genuine
advantages are properties: no stored secret, no certificates, no ground-station round
trip for peer authentication, capture damage bounded to *N−1* links, and a symmetric
core small enough that the hardware-area argument holds.

## Not yet done

- **Formal verification** — the Tamarin model is specified in the paper but not
  mechanically discharged.
- **Realistic radio** — no MAC-layer contention, collisions or retransmissions, so
  network delays are a best case.
- **Hardware** — everything is simulated; no FPGA prototype.
- **Side-channel analysis** — not performed for the two in-tree primitives.
